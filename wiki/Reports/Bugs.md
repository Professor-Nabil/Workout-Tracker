# Project Bugs and Technical Hurdles

This document chronicles the significant technical challenges, bugs, and obstacles encountered during the development of the Workout Tracker API, serving as a post-mortem to prevent regression and document our "Bulletproof" learning process.

---

## 1. Integration Test Instability (Dynamic DB)

- **Problem**: Running multiple test files in parallel caused race conditions in the shared MariaDB test database.
- **Root Cause**: Tests were attempting to use the same database, leading to data collisions.
- **Solution**: Implemented a dynamic database lifecycle in `tests/lib/test-db.ts`. Each test file now provisions its own isolated database instance using the MariaDB CLI, ensuring parallel execution stability.

## 2. API Schema and Route Conflict

- **Problem**: Overlapping route definitions in `workout.route.ts` caused the generic parameterized route `/:workoutExerciseId` to incorrectly intercept the specific sub-route `/reorder`.
- **Root Cause**: Express matches routes in the order they are registered.
- **Solution**: Adjusted the registration order, ensuring more specific paths (e.g., `/reorder`) are registered before generic, parameterized paths.

## 3. OpenAPI Library Incompatibility (Zod v4 vs v3)

- **Problem**: Attempting to auto-generate API documentation using `zod-to-openapi` caused runtime errors: `TypeError: Cannot read properties of undefined (reading 'prototype')`.
- **Root Cause**: `zod-to-openapi` depends on `zod` version `~3.5.1` and performs global prototype modification (`ZodSchema.prototype.openapi`). Our project uses `zod` version `4.4.x`. The library's internal `zod-extensions.js` code fails when it tries to patch the prototype of a Zod version it does not recognize or that has changed internal structures.
- **Resolution**:
  1. Abandoned auto-generation to maintain a stable, "Bulletproof" test suite.
  2. Implemented manual API documentation via a static `docs/openapi.json` file.
  3. Implemented a static `swagger-ui-express` service that serves the manual file.
  4. Removed all conflicting runtime dependencies and build-time generation scripts that relied on the incompatible library.

## 4. Prisma Migration Constraint

- **Problem**: A `500 Internal Server Error` occurred during authentication because the `RefreshToken` token was too long for the default `VARCHAR(191)` column type generated by the initial migration.
- **Root Cause**: The JWT generated in the service was longer than the column limit.
- **Solution**: Updated the `RefreshToken` model in `prisma/schema.prisma` to use `@db.Text` for the `token` field, then performed a migration to adjust the column type.

---

## Summary of "Bulletproof" Strategy

Throughout these issues, the primary takeaway was that **stability and a green test suite are non-negotiable.** We prioritized removing features that caused runtime instability (like the auto-generated docs) in favor of maintainable, manual alternatives that keep the system reliable and testable.
